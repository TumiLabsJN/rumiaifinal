## Bug Description

### Issue Summary

Universal principles in `winning_formulas.json` use an ambiguous string format that omits `bottom_performer_avg`, making it impossible for readers to determine the direction of the gap.

### Current Behavior

```json
"supplementary_insights": {
  "universal_principles": [
    "closing_person_count: avg 3.59 in top performers (gap 21.81)"
  ]
}
```

**Problem**: Reader cannot determine if:
- Bottom performers: 3.59 - 21.81 = **-18.22** (impossible)
- Bottom performers: 3.59 + 21.81 = **25.40** (correct)

### Expected Behavior (from MLPlanningv2.md)

```json
"supplementary_insights": {
  "universal_principles": [
    "High eye contact rate (88% vs 45% for top vs bottom performers) - applies to 78% of videos"
  ]
}
```

**Clear format**: Shows both top AND bottom values explicitly, eliminating ambiguity.

## Root Cause Analysis

### Direct Cause

**File**: `ml_pipeline/stage7_llm_analysis/stage7_preprocessing.py`
**Function**: `generate_universal_principles()` (lines 444-517)

**Bug**: Function extracts `top_performer_avg` and `gap` but fails to extract `bottom_performer_avg` from Stage 6 data.

```python
# Lines 476-493
for feature_data in feature_importance[:top_n]:
    feature = feature_data['feature']
    top_avg = feature_data.get('top_performer_avg')
    gap = feature_data.get('gap')
    # ❌ BUG: Missing this line
    # bottom_avg = feature_data.get('bottom_performer_avg')

    if top_avg is None or gap is None:
        logger.warning(f"Skipping feature '{feature}' - derived feature")
        continue

    # ❌ BUG: Format omits bottom_avg
    principle = f"{feature}: avg {top_avg:.2f} in top performers (gap {gap:.2f})"
    principles.append(principle)
```

### Why Wasn't This Caught?

1. **No Runtime Errors**: Code works correctly, just produces ambiguous output
2. **Internal Consistency**: Format is consistent across all buckets
3. **Human-Only Issue**: Only affects human readers, not machine processing
4. **Spec Deviation**: Implementation deviated from MLPlanningv2.md spec without validation
5. **Amplified by Bug #6a**: Large gaps (21.81) from person detection bug made ambiguity more obvious

### Relationship to Bug #6a

**Bug #6a** (Person Detection Overcounting):
- Caused abnormally large gaps (e.g., 21.81)
- Made string ambiguity more noticeable ("3.59 with gap 21.81" implies impossible -18.22)
- **Is now fixed** (person detection capped)

**Bug #6b** (String Format):
- Exists independently of Bug #6a
- Would still cause ambiguity with small gaps (e.g., "3.59 with gap 1.49" → is bottom 2.10 or 5.08?)
- **Still needs fixing** even after Bug #6a fix
